# The decisions

- **Two PRs, split by layer**, each separated neatly by commits (second round). The first round's *"one pr, separate neatly by commits, then ultrareview at the end"* is superseded; the last ultrareview goes to Rigid-physics (third round).
- **The parity rule** (applies to every row): **match MuJoCo, unless MuJoCo panics, hangs, or silently does something other than the file or call asked — then refuse ("stricter"); or does something we cannot — then refuse ("stated limitation"). Every deviation is listed and documented** in the Intentional Divergences table (`sim/docs/MUJOCO_CONFORMANCE.md`).
- **MJCF parity target: MuJoCo 3.5.0** for loading; the existing golden numeric data stay 3.4.0, and the census gate (second round) adds 3.5.0 goldens beside them. (276 rule cases agree between 3.4.0 and 3.5.0, A5 §0.)
- **Unknown attributes and elements are errors**, with an allowlist of the extensions in-tree code uses; MuJoCo-valid attributes we never implement are errors (stated limitation).
- **Process**: think it out → spec → compact → stress-test the spec → implement off the stress-tested spec.
- **Visual-only and capacity-hint elements: accepted with no effect** (a third verdict), each listed — `camera light material texture visual skin`, `<statistic>` except `meaninertia`, `<size memory njmax nconmax nkey nstack nuserdata>`.
- **Where MuJoCo itself fails, load:** *"wouldnt it make sense to load all 3? parity doesn't mean we have to inherit its bugs"* — a fourth deviation kind, **lenient**: MuJoCo refuses a valid input through its own defect; we load it and list it, **provided a test shows our result is right**. Applies to MuJoCo's 2-body cable refusal. Where such a test cannot be written, the item comes back to Jon. The other two cases first named here have no such test and are refused: the non-converging lengthrange (second round; A11 §LR-3, Q122) and qhull on a flat mesh where MuJoCo needs a hull (A10 §5, Q103).
- **Delay/history (P-L34): implement in Rigid** (MuJoCo 3.5.0's history buffers, delayed actuation and sensors).
- **Second round (2026-10-06):** `xfrc_applied` → MuJoCo's force-first order AND a new type, so 0.9 code fails to compile instead of silently swapping; **split by layer** — two PRs, sim-core physics (incl. cf-geometry collision) then sim-mjcf loading (the last ultrareview: third round); the parity census's new clusters (98 docs, a lower bound — appendix A16) → **isolate and fix all in Rigid**; the census becomes a **permanent executable gate** in Rigid (MuJoCo 3.5.0 per-doc golden data + a ratchet test whose agree count can only rise). Defaults stated and not objected to: P-L32 in Rigid with every other isolated fix; the 4 muscles on unlimited hinges refused (no right value exists, MuJoCo's refusal is intended — Jon's own condition fails); sleep under RK4 — now inside "fix all census clusters".
- **The known divergences: fix in Rigid** — sleep re-forward and sleep timing, dim-3 tet re-orientation, flex boundary flaps, STL vertex deduplication, principal-axis order of a full inertia, hull face order. ⚠ Hull face order comes from qhull (C/C++, excluded by the no-C++ rule); matching its exact order means porting qhull's tie-breaking. The spec matches and tests the hull as SETS (vertices, faces) and keeps our order unless Jon wants the port.

Consequences the rule settles directly: refuse every NaN/±inf number; refuse ball-then-slide; refuse an automatic backwards range; refuse a timestep ≤ 0 or NaN and drop the `> 1` rule; callbacks follow MuJoCo's order and counts; the bad-ctrl check reads the clamped copy; finite differences refuse RK4; **sensor derivatives take MuJoCo's semantics** (C at the current state, A2 Q4; P14 lists the flips).
- **Third round (2026-10-07):** the lenient kind also covers MuJoCo **computing a wrong value** (not only refusing a valid input), when a test against an independent truth — an invariant, physics, MuJoCo's own docs — proves ours right; each is listed with its test. **Plain arithmetic, no FMA emulation** (MuJoCo's arm64 build fuses 8,901 operations, its x86_64 build none, so its exact answer depends on the machine). **MuJoCo's flex meaning**: `<flex body=… vertex=…>` names existing bodies. **The last ultrareview goes to Rigid-physics.**
- **Fourth round (2026-10-07, after stress test round 1):** *"rename that action-space method too, i agree"* — **`xfrc_applied` becomes `Vec<BodyWrench>`** (`BodyWrench { force, torque }`, named fields, with no `Index`, `Deref` or `From<Vector6>`), **and sim-ml-chassis's `ActionSpaceBuilder::xfrc_applied(body_range)`** (`sim/L0/ml-chassis/src/space.rs:821`) **is renamed `body_wrench(body_range)`**, its action laid out `[force, torque]` per body and the `Injector::XfrcApplied` variant renamed to match — so 0.9 code that uses either fails to compile instead of silently swapping.
